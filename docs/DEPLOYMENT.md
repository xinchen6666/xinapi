# xinapi 单机 Docker 部署设计

本文说明单机拓扑、运行边界及后续发行交接。首次安装按 [单机 HTTPS 手册](INSTALL.md) 执行，本机基础运行见 [Compose 手册](COMPOSE.md)。任务定义见[开发计划](PLAN.md)。

## 拓扑与数据

| 服务 | 进程与网络 | 持久化、秘密与责任 |
| --- | --- | --- |
| `new-api` | React 资源随 Go 服务发布；唯一应用入口，默认只绑定宿主回环，由 HTTPS 反代对团队开放 | 成员、权限、内部 Client Key 映射和 OAuth 操作记录属于 New API。会话、加密及内部服务密钥从受保护配置注入 |
| `cpr` | Rust 服务单副本；内部管理与推理接口只允许受信调用方。部署者提供 Mihomo 官方制品，以只读方式挂载，CPR 将其作为同容器子进程运行 | CPR 是上游账号、OAuth 凭据、出口绑定权威；运行数据、会话锚点和持久绑定保存在命名卷 |
| `postgres` | PG 18；不发布宿主端口；`newapi`、`cpr` 分库、分应用用户 | 由专用初始化身份建库授权，不让两应用以数据库超级用户运行。两个逻辑库为一套关联备份，备份离机、加密 |
| `redis-newapi` | 内网，认证独立 | New API 的会话缓存与限流等；恢复行为按 New API 合同验证 |
| `redis-cpr` | 内网，认证独立 | CPR 的租约、亲和、OAuth pending 等短期状态；恢复不能复活旧授权或在途请求 |

默认五个服务，不含团队已有的 HTTPS 反代。没有域名时先做本机隔离演练，对朋友开放前完成 TLS。CPR 的原生 `/readyz` 与 `/healthz` 仅作内部探测；单账号额度耗尽不应触发整套重启。应用启动要容忍依赖未就绪，不能只依赖 Compose 的启动顺序。

Mihomo 不使用 Docker socket、TUN、host network 或特权模式。CPR 容器运行非 root，使用 init、受限可写目录、日志轮转和进程预算。每账号受管入口和内核 controller 绑定容器回环；不要为了给管理员浏览器登录而把全段端口对公网发布。需浏览器同出口时，应有显式受控的临时访问方式，且与服务器流量分别观测。

### 引擎入口运行参数

X08 入口由账号或授权预留项独立拥有，只监听 CPR 回环地址。`CPR_MIHOMO_BIN` 指定只读挂载的制品路径（默认 `/app/bin/mihomo`）；当前准入固定为官方 v1.19.33 linux/amd64-compatible 的已登记 ELF。启动校验摘要和平台，执行已核验文件句柄，并以本次 controller 凭据核对实际版本。其他制品或平台返回明确准入错误。

`CPR_ENGINE_MAX` 默认为2，取值1–4；`CPR_ENGINE_PORT_BASE`／`CPR_ENGINE_PORT_SPAN` 默认为24000／200，范围为高端口连续偶数跨度；`CPR_ENGINE_START_TIMEOUT_MS` 默认为15000，范围1000–30000。启动预算覆盖排队和制品校验，取消后监督任务继续回收。每入口 stdout/stderr 各保留至多1MiB，超额输出持续排空。

Compose 默认设置 `XINAPI_CPR_MEMORY_LIMIT=1g`、`XINAPI_CPR_CPU_LIMIT=2.0` 与256个PID；此预算覆盖整个CPR容器。实例容量结论以[修复验证](worklog/X08-fix.md)的单／双实例观测为准，4实例及持续压力留待验证。

入口登记位于运行数据卷 `engines/entries.json`，保存稳定端口、归属、批准版本与私有入口凭据，文件0600、目录0700。升级把v1节点登记转为端口占位，owner为空，原端口继续保留；新账号或预留项建立独立入口。登记缺失、损坏或写失败时拒绝分配，保留原文件供恢复。凭据留在受限服务端目录，API只返回公开观测。Mihomo按[制品登记](../third_party/mihomo.lock.json)由部署者提供只读挂载，许可与对应源码资料见[上游清单](UPSTREAM.md)。

### 受管路由操作

X09通过prepare→approve发布账号出口，operation_id用于读回结果。候选验证临时使用一个引擎槽，需在当前运行实例之外预留容量。默认出口探测服务保持原值，部署者可用 `CPR_PROXY_PROBE_URL` 指向自建受信JSON服务，响应形如 `{ip:"地址"}`；隔离演练使用此入口，业务管理员只选择已批准节点。

CPR重启后先GET读取operation与当前引擎事实，再显式reconcile恢复已发布固定版本。applying表示数据库与引擎提交边界待确认；abort可终结候选并尝试恢复原入口。换路采用明确终止旧HTTP2／WS在途连接的策略，后续请求按新出口代次选连接池。已发布受管账号的普通删除与账号敏感导出受保护；退役流程另行安排。接口见[受管路由](../services/codex-proxy-rs/docs/api.md#16-账号受管路由与换路)。

### 管理员OAuth与回执

管理员在New API账号与出口页面的授权页签选择provider、名称和已批准节点，系统先验证独立入口再返回第三方授权链接。已有受管账号通过重新授权沿用当前专用路由。浏览器回调只提交一次，页面刷新或网络中断后使用同登录会话读取回执；unknown需要确认已有结果或显式发起新操作。授权期限10分钟，完成回执保留24小时，两个期限分别判断。

过期或明确结束的未知预留可显式取消，系统核对零账号／代理／路由引用后回收。授权完成已保存的账号保持保护；服务重启后使用对应operation_id执行受管路由reconcile恢复入口。CPR执行追加0049迁移，New API沿既有AutoMigrate创建CprOAuthOperation表。

公开部署使用HTTPS、SESSION_COOKIE_SECURE=true与精确SESSION_COOKIE_TRUSTED_URL。真实管理员身份与登录会话由New API保存，CPR服务Key留服务端，授权表单沿既有Origin与权限检查。第三方浏览器登录与服务器交换的网络出口分别确认；回调、state与令牌始终保留在私有调用范围。接口详见[授权操作](../services/codex-proxy-rs/docs/api.md#17-管理员托管oauth与只读回执)。

## 计划交付物

X02–X04：两个可独立构建的源码树、锁文件、应用镜像构建定义、根 `compose.yaml`、不含有效凭据的 `.env.example` 和初始化流程。X08 增加 Mihomo 平台制品清单、摘要验证、第三方许可/对应源码资料。X16 补齐 HTTPS 反代示例、干净主机安装步骤、管理员首次使用与故障排查。X17 补齐备份恢复演练；X18 提供 release 说明、确切提交、镜像标识与已验证的平台。

镜像名称、操作脚本和宿主环境的具体命令以相应任务实际交付为准。不要在手册中假设凭据以 `*_FILE` 自动生效：若上游不支持，则在启动适配中验证读取和文件权限。真实 `.env`、配置、节点密钥与备份不纳入 Git 或日志；不要把展开的 Compose 配置当作公开证据。部署用数据库/磁盘本身也需保护，原 CPR 凭据不是因使用 Docker 就自动静态加密。

## 首次安装

从新克隆按 [单机 HTTPS 安装](INSTALL.md) 操作。该手册覆盖本地明确版本的镜像、私有配置、Mihomo 只读挂载、宿主 HTTPS、首次管理员和成员调用。先在隔离环境核对业务路径，再按实际授权开放团队访问；公网出口与第三方授权的覆盖以对应运行记录为准。

## 日常操作与故障判断

- **订阅未能更新：**区分下载/解析失败（继续上次已批准快照并标陈旧）和成功刷新发现绑定节点消失（停止新出站）。不要删除代理后继续尝试默认出口。
- **账号无法调用：**分别看成员授权、账号额度与凭据、路由版本、引擎健康、实际出口观测。代理能探测到公网不代表账号能授权。诊断通过 request ID 关联；公开只留脱敏证据。
- **资源上升：**看受管引擎数、RSS、PIDs、流连接和端口冲突，容量依据 X08/X15 的实测。CPR 不通过复制同一账号池容器来扩容。
- **维护停机：**先挡新请求，通知成员，按应用能力排空或明确切断在途流，再停旧 CPR 和子进程，确认唯一活跃实例才升级。上游 Compose 的 75 秒停止宽限是初始参考，不保证 SSE/WS 不断；最终值依据实测清理预算。不要用 `docker compose down -v` 作为默认排障或升级命令。

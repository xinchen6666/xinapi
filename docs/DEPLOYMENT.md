# xinapi 单机 Docker 部署设计

本文是 X04、X08、X16–X18 的交付规范。**X01 只有文档：此时克隆仓库不能执行下面的启动步骤。** 等相应 Compose、镜像构建、初始化脚本和测试完成后，X16 用新主机实测并把本文变成带实测版本的运维手册。任务定义见[开发计划](PLAN.md)。

## 拓扑与数据

| 服务 | 进程与网络 | 持久化、秘密与责任 |
| --- | --- | --- |
| `new-api` | React 资源随 Go 服务发布；唯一应用入口，默认只绑定宿主回环，由 HTTPS 反代对团队开放 | 成员、权限、内部 Client Key 映射和 OAuth 操作记录属于 New API。会话、加密及内部服务密钥从受保护配置注入 |
| `cpr` | Rust 服务单副本；内部管理与推理接口只允许受信调用方。Mihomo 固定版本随镜像或校验证明的构建步骤提供，是同容器子进程 | CPR 是上游账号、OAuth 凭据、出口绑定权威；必要本机运行数据、会话锚点和持久绑定不能只放临时层 |
| `postgres` | PG 18；不发布宿主端口；`newapi`、`cpr` 分库、分应用用户 | 由专用初始化身份建库授权，不让两应用以数据库超级用户运行。两个逻辑库为一套关联备份，备份离机、加密 |
| `redis-newapi` | 内网，认证独立 | New API 的会话缓存与限流等；恢复行为按 New API 合同验证 |
| `redis-cpr` | 内网，认证独立 | CPR 的租约、亲和、OAuth pending 等短期状态；恢复不能复活旧授权或在途请求 |

默认五个服务，不含团队已有的 HTTPS 反代。没有域名时先做本机隔离演练，对朋友开放前完成 TLS。CPR 的原生 `/readyz` 与 `/healthz` 仅作内部探测；单账号额度耗尽不应触发整套重启。应用启动要容忍依赖未就绪，不能只依赖 Compose 的启动顺序。

Mihomo 不使用 Docker socket、TUN、host network 或特权模式。CPR 容器运行非 root，使用 init、受限可写目录、日志轮转和进程预算。每账号受管入口和内核 controller 绑定容器回环；不要为了给管理员浏览器登录而把全段端口对公网发布。需浏览器同出口时，应有显式受控的临时访问方式，且与服务器流量分别观测。

### 引擎入口运行参数

X08 的入口按已批准节点启动 Mihomo 子进程，只监听 CPR 回环地址。部署参数：`CPR_MIHOMO_BIN` 指定制品路径（默认 `/app/bin/mihomo`），`CPR_ENGINE_MAX` 限制并行实例（默认 4），`CPR_ENGINE_PORT_BASE` 与 `CPR_ENGINE_PORT_SPAN` 划定入口与控制面端口（默认 24000/200），`CPR_ENGINE_START_TIMEOUT_MS` 控制就绪等待（默认 15000）。入口记录在运行数据卷 `engines/entries.json`，重启后保持原端口；引擎进程随 CPR 容器回收。

本轮实测单实例 RSS 约 42MB、冷启动 52ms，容量按此估算。Mihomo 制品由部署者取自登记的发布包，镜像内暂不打包；正式分发前按[上游清单](UPSTREAM.md)补齐许可与对应源码资料。

## 计划交付物

X02–X04：两个可独立构建的源码树、锁文件、应用镜像构建定义、根 `compose.yaml`、不含有效凭据的 `.env.example` 和初始化流程。X08 增加 Mihomo 平台制品清单、摘要验证、第三方许可/对应源码资料。X16 补齐 HTTPS 反代示例、干净主机安装步骤、管理员首次使用与故障排查。X17 补齐备份恢复演练；X18 提供 release 说明、确切提交、镜像标识与已验证的平台。

镜像名称、操作脚本和宿主环境的具体命令以相应任务实际交付为准。不要在手册中假设凭据以 `*_FILE` 自动生效：若上游不支持，则在启动适配中验证读取和文件权限。真实 `.env`、配置、节点密钥与备份不纳入 Git 或日志；不要把展开的 Compose 配置当作公开证据。部署用数据库/磁盘本身也需保护，原 CPR 凭据不是因使用 Docker 就自动静态加密。

## 首次安装清单（待实测）

1. 选定仓库的固定提交或已验收标签。在干净 Linux 测试机记录 CPU 架构、内存、磁盘、Docker Engine／Compose 版本及可用性；未测架构不标支持。若机器已有业务，避免端口、卷和项目名冲突。
2. 用受保护的本地生成流程创建 PostgreSQL、两个 Redis、New API 会话/加密、CPR 管理及节点秘密保护所需的不同密钥；文档只保留引用。空卷建两个库和对应权限，已有卷时不覆盖数据、不自动换密码。保存控制台及内部服务引导方式；不使用样例口令。
3. 限制 Docker 网络与挂载访问；仅 New API 可经团队入口访问。配置精确的 HTTPS Origin、可信反代、SSE 禁缓冲、WebSocket 升级及长请求超时。CPR 有出站网络不等于可忽略账号的强制出口策略。
4. 在仓库根执行 `docker compose config --quiet` 检查配置，再执行 `docker compose up -d --build --wait`，用 `docker compose ps` 核对五服务。各镜像、源代码与依赖应能对应到同一发布记录；不使用未固定的在线自动更新覆盖镜像。
5. 用 New API 状态接口、CPR 内网就绪接口验证启动；然后验证管理员登录、普通成员无法访问管理接口，以及真实浏览器可同时收到 SSE 和完成 WS 升级。健康探针通过不能替代这三项。
6. 先走自造订阅演示。正式试用时由管理员提供受保护来源和获授权的测试账号；测试绑定、IPv4/IPv6 观测、令牌刷新、两成员权限和重启恢复后再放行。不同节点落到同一公网 IP 时记录不满足，不改成功标准。

## 日常操作与故障判断

- **订阅未能更新：**区分下载/解析失败（继续上次已批准快照并标陈旧）和成功刷新发现绑定节点消失（停止新出站）。不要删除代理后继续尝试默认出口。
- **账号无法调用：**分别看成员授权、账号额度与凭据、路由版本、引擎健康、实际出口观测。代理能探测到公网不代表账号能授权。诊断通过 request ID 关联；公开只留脱敏证据。
- **资源上升：**看受管引擎数、RSS、PIDs、流连接和端口冲突，容量依据 X08/X15 的实测。CPR 不通过复制同一账号池容器来扩容。
- **维护停机：**先挡新请求，通知成员，按应用能力排空或明确切断在途流，再停旧 CPR 和子进程，确认唯一活跃实例才升级。上游 Compose 的 75 秒停止宽限是初始参考，不保证 SSE/WS 不断；最终值依据实测清理预算。不要用 `docker compose down -v` 作为默认排障或升级命令。

## 备份、恢复和发布门槛

| 演练 | 操作 | 必须留下的证据 |

| 备份 | 维护窗口冻结相关写入，记录两库快照、必要卷、配置版本、镜像 digest；密钥单独备份并限制权限 | 备份标识、时间点、校验结果和可用解密流程，不公开数据本身 |

| 升级 | 保留旧镜像和对应数据快照，先在恢复副本演练迁移，再作单实例替换 | 版本/迁移差异、维护中断时间、探针和真实功能验收结果 |
| 回退 | 若新旧 schema 兼容按实测路径切回；否则恢复与旧代码匹配的两库和运行状态，并检查新旧密钥兼容 | 回退后的版本、最近可恢复时间点、丢失窗口说明和验证 |
| 发布 | 干净克隆按本文完成演练；复核 X01–X18、V01–V20、许可和未测项 | GitHub commit/PR/tag、来源和制品摘要、发布说明及限制 |

这些均为计划，不是部署结果。仓库写入授权不等于允许访问集群、真实服务器、注册表或真实账号。回到[项目状态](STATUS.md)查看哪些实际发生过。

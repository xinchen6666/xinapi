### 实际操作和结果

1. **配置与空卷。**生成专属私有配置，`docker compose -p xinapi-x04-review config --quiet` exit 0；执行 `up -d --build --wait --wait-timeout 100`，7.95 秒 exit 0。随后独立访问接口并完成真实认证。New API 在首次建库阶段重启 3 次后恢复，CPR 启动成功。根配置明确五服务；`newapi-data`、`cpr-data` 为内部网络，应用间通过 `gateway` 通信。PG18 卷挂载 `/var/lib/postgresql`，实际 PGDATA 为 `/var/lib/postgresql/18/docker`。
2. **数据库权限。**`newapi`、`cpr` 各使用自己的同名库和角色，均为 `rolsuper=f`、`rolcreatedb=f`、`rolcreaterole=f`、`rolreplication=f`、`rolbypassrls=f`。迁移各形成 38 张 public 表。以有效口令连接对方库、`postgres`、`template1` 均 exit 2，返回数据库权限拒绝。两库分别建立审核记录，后续重建仍可读回。
3. **Redis 认证。**两实例自有口令返回 PONG；空认证返回 NOAUTH；交换两套口令均返回 WRONGPASS。同名演练键分别保存各自内容，AOF 启用，重建后读回各自原值。
4. **权限和秘密注入。**配置目录 0700，五个服务环境文件 0600；PG 数据目录 0700。当前使用 Compose `env_file` 直接注入，各应用真实认证证明相应配置被消费，`*_FILE` 路径属于本轮未采用方式。CPR 以 UID/GID 10001 运行，启动脚本把生成的初始口令渲染到私有 tmpfs：目录 0700、配置 0600；使用该口令实际登录成功。宿主普通 UID 65534 读取私有配置和管理 Key 均被权限拒绝。公开挂载脚本分别为 0755、0644，模板为 0644，CPR 容器内成功读取；宿主父目录仍保持自身访问限制。公开目录、公开配置文件、必填字段缺失和半套配置四种输入均使配置生成器 exit 1，提示保留已有配置及凭据。
5. **网络边界。**通过容器监听表、实际 HostPort 和独立外部 Docker 网络发起 TCP 连接。New API 仅发布回环端口；CPR、PG、两个 Redis 发布为空。外部网络对宿主网关和宿主外部网卡的 19304、8080、5432、6379、7890、7891、9090 共 14 项连接均失败；直接连接五服务容器地址的 5 项也失败。分别共享两应用网络命名空间验证：各自 PG 与 Redis 可连，对方 Redis 拒绝连接，New API 至 CPR 内网可连。CPR 当前业务监听仅 8080，代理入口属于后续 X08。宿主回环 HTTP 请求成功。本轮外部边界为同机独立网络，异机及公网 IPv6 验证标为 `not_run`。
6. **两层管理员。**在 New API 完成首次引导，管理员身份 role=100，创建普通成员并登录核对 role=1。成员访问 `/api/user/` 返回 403。通过 CPR 容器内回环 API 登录 `admin@cpr.local`，首次签发管理 Key 并存入部署者私有 0600 文件；以该 Key 调用管理接口成功。匿名、错误 Key、New API 管理员令牌和成员令牌访问 CPR 管理接口均返回 401。两应用错误口令均被拒绝。CPR 管理 Key 的 New API 后端消费及统一管理页面属于 X05。
7. **保留卷。**执行常规 `down`、重新运行配置生成器和 `up -d --wait --wait-timeout 60`，7.93 秒 exit 0。生成器报告沿用原配置。两库审核记录、两套 Redis AOF 演练值、New API 初始化状态、管理员和成员原口令、CPR 原管理员口令及原管理 Key 均继续有效；CPR `/readyz` 204。
8. **依赖延迟与故障。**独立项目 `xinapi-x04-delay` 仅为 `redis-newapi` 的入口加入 45 秒延迟；其余使用原 Compose。`up -d --wait --wait-timeout 60` 在 8.37 秒 exit 0，此时 New API 请求为 ConnectionResetError，Redis 认证命令 exit 1；54.58 秒后 New API 可用，累计重启 8 次。另在健康审核项目停止 CPR Redis，CPR `/readyz`、`/healthz` 均返回 503，New API 状态仍为 200；Redis 恢复后 CPR `/readyz` 返回 204。
9. **异常初始化。**独立项目 `xinapi-x04-incomplete` 使用真实 PG18，构造已有 PG_VERSION、newapi NOLOGIN 角色及单库审核记录、缺少完成标记的半成品状态。根入口持续返回 `Incomplete xinapi cluster initialization; inspect startup logs and preserve volume.`。首次单 PG 的 `up --wait` 曾 exit 0 并显示 Healthy，随后观察到 Restarting(1)；启动全部五服务并限时 15 秒，exit 1。停止项目后，以原管理身份在独立维护容器中读回 `partial-retained`；重复首次 CREATE ROLE 命令返回 exit 3、角色已存在。原数据保持，自动重置行为为零。半成品卷仍保留，原卷补全流程待修订和复验。

### 必修发现

- **P2：启动成功与真实就绪存在时间差。**[Compose 依赖声明](../../compose.yaml#L59)仅控制顺序；New API、PG 与两个 Redis 缺少供 `--wait` 使用的健康结果。[运行手册](../COMPOSE.md#L30)以 `up -d --wait` 和 `ps` 收尾。上面的 45 秒 Redis 延迟与半成品 PG 两个场景均出现过提前 exit 0，影响部署者对可用性的判断。修正目标：启动完成条件覆盖应用接口和真实服务认证，缺项或超时明确返回失败；修订后重复原触发场景。
- **P2：半成品原卷补救路径缺项。**[拒启入口](../../compose.yaml#L30)和[初始化 SQL](../../deploy/compose/init-db.sh#L9)会保留半套状态；[手册现有说明](../COMPOSE.md#L51)只指导保留卷和查看日志。已有角色时直接重跑会再次失败。修正目标：给出受控维护启动、辨识已完成阶段、沿用原凭据补齐角色/库/ACL、通过真实认证后写完成标记的步骤，并在保留原记录的卷上验证。当前的明确拒启和数据保留保护继续保留。

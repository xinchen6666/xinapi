# X04 单机 Compose 联调

负责人：lead。开发分支 `task/X04-compose`，依赖 X03 CPR 版本修订。交付范围：根 Compose、本地配置生成、PG18 首次分库授权、独立 Redis，以及本机首次管理员流程。沿用现有 X03 镜像和两个应用的原配置合同。

本地演练采用独立项目名、端口、生成的本机凭据与命名卷，业务应用仅含实验数据。协作入口与长期记忆中原有的本地编辑独立保留。

## 实际结果（2026-11-23，Asia/Shanghai）

- Linux/amd64，本机项目 `xinapi-x04-local`。使用 X03 New API 和 CPR 修订镜像、PostgreSQL 18.7、Redis 8.10.3。Compose 配置解析通过；先启动数据层，再启动应用并等待 CPR 就绪。
- New API 在回环端口 18304 返回成功状态，首次安装接口报告 postgres。用本地演练身份完成首次初始化及登录。New API 容器内调用 `http://cpr:8080/readyz` 成功；CPR 首次管理员通过内部会话 API 登录成功。
- 两个应用角色各自在自己的库建立了 38 张 public 表，超级用户、建库、建角色权限均关闭。用各自有效口令连接对方库均被数据库权限拒绝。
- 两套 Redis 各自通过带认证的读写，空认证请求返回 NOAUTH，交换两套密码返回 WRONGPASS。两个实例写入同名、异值的演练键，在容器重建后各读回自己的值，随后清理该键。
- 执行常规 `down` 保留卷，再次运行配置生成器并 `up -d --wait`。五个容器成功重建，两层管理员仍能分别登录。实际绑定仅 New API 的 `127.0.0.1:18304`；CPR、PG、两套 Redis 宿主绑定为空。
- 首轮在严格宿主 umask 下，公开初始化脚本读取失败。现已落实脚本权限及手册中的权限命令；早期半成品 PG 卷触发明确拒启提示，修正后换独立空卷完成验证。失败演练项目已停，保留其命名卷供部署者处理。
- 配置目录 0700、服务文件 0600；临时配置目录实例验证缺项时退出。所有本地口令和登录响应留在受保护环境，公开记录仅含结果。

当前演练保持运行；使用[运行手册](../COMPOSE.md)管理，同机入口为 `http://127.0.0.1:18304`。演练 New API 用户名 `x04operator`，口令在本机受保护的 `.runtime/x04-local-dev/demo-operator.env`。管理密钥的首次签发与后端消费按手册和后续 X05 分工。范围仅为单机基础设施与启动认证，真实账号、订阅、成员权限和固定出口分别在后续步骤开发。

[X04 PR #3](https://github.com/xinchen6666/xinapi/pull/3) 以 X03 分支为审阅目标。首次分支 CI 的项目内容检查将两个 Python URL 模板识别为凭据形状，实际随机值仅存在于私有目录。生成器改用标准 URL 组件拼装，原扫描规则保留。临时实例逐项确认生成的地址、身份、口令和数据库与服务配置相符。

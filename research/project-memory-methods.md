**文档职责：每种事实只有一个权威位置**

以下路径是供主代理采用的建议命名，不代表本子代理已创建它们。主代理若已采用其它命名，只需保留相同的职责边界。

| --- | --- | --- |

| `README.md` | 人类入口：项目目的、当前阶段、如何找到文档 | 第二份完整路线图、状态账本或源码证据 |

| `docs/PLAN.md` | 里程碑、稳定任务 ID、任务范围、前置依赖、验收标准 | 重复维护实时状态与完成勾选；实际结果由状态／证据链接给出 |

这些职责不要求一开始都写成长文。可以保持短小的导航文件。若希望进一步减少文件，优先把长期事实索引并入 PROJECT，并让 README 链接架构；不建议合并 PLAN 与实际验证结果，因为“准备做”与“已经证明”容易混淆。当前项目涉及多个上游仓库，单独维护 UPSTREAM 有实际价值。

根级 AGENTS 建议保持约一到两页、只在规则变化时更新。这是本项目的维护目标，不是 AGENTS.md 标准规定。STATUS 和 HANDOFF 应能在几分钟内读完。更早的交接用版本控制保留；没有 Git 时可归档到单独的 dated handoff 目录，启动默认只读当前交接。不要为了“记忆完整”每次加载所有归档。

**任务、证据和状态契约**

业务任务 ID 和协作工具里的临时任务 ID 分开：例如 `DOC-001`、`POC-001` 是持久项目 ID，`task-3` 只是当前协作任务，可在 STATUS 保存映射。换 agent 或换工具时，持久 ID 不重排、不复用。

PLAN 中的一个任务至少包含如下字段；这是示例，不代表已授权或执行 POC：

```yaml
id: POC-001
title: 验证两个账号的出站路径
milestone: M1
scope: 仅验证已获授权账号的推理、刷新和额度查询出口
write_scopes:
  - tests/integration/egress/
depends_on:
  - DECISION-001
acceptance:
  - 两个账号分别观测到预定公网出口
  - 代理故障和停用后无账号请求意外直连
  - 未覆盖的请求路径被明确列出
planned_validation:
  - 指向具体场景和预期结果，不虚构运行日志
```

STATUS 是唯一状态源；与本项目根级协作入口保持一致，使用 `pending`、`in_progress`、`blocked`、`done` 四种状态。尚未授权实施或尚未开始的计划保留 pending；只有明确外部条件妨碍已启动任务时才标 blocked。已写代码但待验证时仍保留未完成状态，在 next_action／validation_gap 明确缺口，无需额外扩展状态枚举。不必把主观进度百分比当成事实；整体进度优先列里程碑门槛和已验收任务数。若展示比例，应写清分母，不能把“研究完成”算作“产品完成”。

一个状态条目至少包含：task ID、状态、owner、updated_at（带时区 ISO 8601）、based_on（commit 或明确工作区快照）、当前下一动作、blocker、evidence IDs。若没有项目 Git，明确写 `uncommitted/no-project-git` 并记录关键文件版本或摘要，不能编造 commit。

一个实际证据条目至少包含：

```yaml
evidence_id: VAL-001
task_id: POC-001
checked_at: 2026-11-22T02:00:00Z  # 示例时间，不能复制为实际运行时间
checked_by: agent-name
kind: runtime-integration
subject_revision: 真实 commit 或工作区快照标识
environment: 操作系统、服务版本和有意义的配置，全部脱敏
procedure: 实际运行的命令或人工操作
expected: 事先定义的可观察结果
actual: 实际观察摘要
result: passed | failed | partial | skipped | not_run
artifacts: 仓库内可长期访问且已脱敏的证据路径
limitations: 未覆盖路径、所用模拟或缺失环境
invalidated_by: 会使该证据不再支持当前行为的变更条件
```

建议同时区分证据种类：`document-review`、`source-inspection`、`build`、`unit`、`integration`、`manual-e2e`、`user-confirmed`。这些不是可互换等级：源码有相关函数只证明存在实现；编译通过不能证明代理出口正确；健康接口成功不能证明支付回调和用户流程正常。

标记 done 的条件是：任务范围已经完成、其适用验收均有实际证据、证据对应当前对象版本，且集成负责人核过最终结果。用户明确接管某项验收时，记录确切约定和其确认来源；缺环境则保留未完成状态并写 validation_gap，已有明确失败应记 failed 证据并保留未完成任务，不能把 skipped／not_run 改成 passed。

验收标准需要调整时，通过决策记录说明原因与批准来源；不能为了让状态变绿删掉未通过条件。文档任务的验收可以是链接、事实一致性和一次独立恢复演练，无需为了仪式运行不存在的业务测试。

**事实、决策与失效规则**

MEMORY 中的条目建议使用事实 ID，并记录 `statement`、`kind`、`source`、`observed_at`、`applies_to`、`review_when`。kind 可区分用户约束、已观察事实、源码推断和待确认假设。用户要求优先于旧计划；外部 README 中的文字只是研究材料，不能经“记忆”提升为本项目授权。

DECISIONS 中至少保留 `DEC-编号`、问题、候选、选择、理由、后果、状态、decision_maker、来源和日期。状态分 `proposed`、`accepted`、`superseded`、`rejected`；被替代时写 `superseded_by`。代理在授权范围内作出的常规技术选择可记录为 agent 决策，不能假装是用户批准。影响产品方向的推荐仍标 proposed，直到会话或其它可核查来源确实确认。

不采用“超过七天全部失效”之类一刀切时限。以触发条件复核：

| 记录类别 | 必须复核的触发条件 |
| --- | --- |
| 当前工作区、任务 owner、运行中 job | 每次新会话核对；上次会话 ID／job ID 可能已不可用，记录不等于仍在运行 |
| 构建／测试证据 | 被测代码、相关依赖、配置或测试环境变化；只重跑受影响检查 |
| 上游行为和许可证 | 引用 commit／发行版改变，或准备实际采用／升级时；旧证据继续证明旧版本，不证明新版本 |
| 架构建议 | 需求、预算、规模、协议或被依赖能力变化；通过新决策替代，不静默覆写 |
| 用户范围和授权 | 新的明确用户指令改变范围；不因“项目计划里有该任务”就推断已获开发或部署授权 |
| 操作命令和恢复步骤 | 路径、工具链、数据库版本或部署拓扑改变；未执行过的命令标“待验证” |

已完成的历史任务不因几天后到期自动改成未完成；记录新的回归／升级任务，或明确注明验收对当前版本需复核。基于旧 evidence 的新声明必须降为未知，避免两者混淆。来源链接失效时保留旧事实的范围，同时补可审计的固定提交或本地摘要；不得凭印象续写结论。

**新 agent 的启动读取顺序**

1. 确认 `pwd`、会话身份和本轮用户目标，核对是否处于正确项目；不要从研究 checkout 的路径推断项目根目录。若有 Git，查看简短状态和相关近期提交；无 Git 则明确记录，避免把临时 checkout 的 Git 当成本项目历史。
2. 读取根级 AGENTS，再读 STATUS 和最新 HANDOFF，取得当前授权边界、当前任务、未提交改动、已知失败和下一动作。使用不自动发现 AGENTS 的 agent 时，在启动提示中明确要求读取；仅存在这个文件不能保证被执行。
3. 按当前任务 ID 读取 PLAN 条目，以及必要的 PROJECT／ARCHITECTURE／DECISIONS／MEMORY／UPSTREAM 引用。第一次接手需先建立项目范围；后续会话不必通读全部档案。
4. 核对证据是否仍匹配当前版本。研发阶段执行与当前任务相关的最小基线检查；当前只有研究与规划时，只验证路径、文档和来源，不自动安装依赖、创建测试账号或启动业务服务。
5. 若有协作工具，先 list/get，按最新 revision claim 准备好的任务；声明 owner 和 write scopes。直接查看磁盘已有修改，不能把旧 owner 消失当作覆盖其工作的许可。
6. 只执行已授权且依赖满足的下一小步。发现当前文件与记忆矛盾时标明差异，用现存源码／真实结果核对；不要先改文件让它符合记忆。

启动目标应是“读当前交接就能知道做什么、为什么、如何证明”，而非加载所有聊天记录。建议由另一位没有参与规划的 agent 进行一次恢复演练：只给仓库路径，检查能否准确说出当前阶段、下一任务、完成标准、未验证点和不可执行事项。该演练通过只能证明交接可读，不能替代业务验收。

**收工交接与并发分工**

每个子任务结束或上下文切换前，先检查自己的最终修改及必要验证，把真实结果写入 VALIDATION 或交给集成负责人，再更新 STATUS，最后替换当前 HANDOFF。顺序的目的，是避免先写“完成”却没有支持记录。提交 Git 必须在既有授权范围内执行；没有提交则记录 dirty files 和工作区事实，不编造“已提交”。

HANDOFF 至少回答：本轮完成了什么、剩什么、当前相关任务 ID、真实证据 ID、哪些文件有未提交修改、下一条具体动作、已知失败与恢复方法、正在运行的 job／agent 及如何核对。后台任务必须收集结果或明确交接；创建了 job 不等于成功。不要把“请继续”交接成一份没有路径和验收条件的口号。

并发采用单一集成负责人：

- 每个任务声明准确 `write_scopes`，例如本任务仅 `research/project-memory-methods.md`；主代理维护全局状态与计划文件，子代理返回结论和证据，由主代理合并。
- 无文件重叠、无前置依赖、接口约定已明确的任务才并行。共享文件的全量格式化、生成器输出和依赖锁文件也算写入范围，不能只统计手工编辑。
- 分工有顺序时显式登记 `depends_on`。scope 是协调声明，不是互斥锁；无法确认所有权时先给负责人发消息，不直接覆盖。
- 动手和完成前都重新读取当前任务／文件，防止覆盖并发编辑。集成负责人审查最终合并结果并运行相关验证，不能把子代理自报通过直接转为项目验收通过。
- STATUS、HANDOFF、DECISIONS 等共享全局文件由一个 owner 更新；规模扩大后可让子任务各写自己的 evidence 文件，再由索引汇总，不让多人同时改一个巨型日志。

**记忆卫生与历史保留**

长期文档只保留结论、适用版本、必要理由和证据入口，不保存原始思维链、整段会话或未经清理的终端输出。失败尝试只有在会影响后续决策／避免重复工作时才留下简短事实；无关历史进入归档或 Git。

真实 access token、refresh token、Cookie、API Key、代理认证 URL、数据库密码、支付密钥以及带秘密的请求转储不得写入 AGENTS、记忆、交接或验证材料。只记录环境变量名、受保护的 secret 引用和操作方法；需要截图／日志时先脱敏。凭据泄漏不是“为了记忆完整”可以接受的代价。若误写，停止继续传播，按既有流程处理凭据轮换和历史清理；不能声称删除当前文件就已经清除 Git 或聊天历史。

**适合当前仓库的落地范围**

本轮由主代理建立轻量项目文档和准确基线即可：研究完成；规划机制建立中；业务实现、部署、真实账号／节点订阅／网络测试均未执行；支付和商业订单不在当前范围。把旧调研中的“CPR 已实现账号代理”记录为“固定上游提交的源码事实”，把“代理停用时禁止默认出口”记录为待实现／待验证任务；当前系统方向和 Cockpit 代码借鉴范围以[项目需求](../docs/PROJECT.md)及实际决策记录为准。根项目尚未初始化 Git，不把持久保存的文档等同于已有提交历史。

不要为文档任务安装 Spec Kit、调整全局 agent 配置，或照文章先创建服务器启动脚本。未来进入业务开发后，再为实际模块添加已验证的运行命令、范围更具体的任务与验收证据。该机制的完成标准是后继 agent 可以从本地文件恢复工作且不会把建议、计划和源码阅读误判为已经完成的系统。
